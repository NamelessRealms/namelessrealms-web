### 裁決點 ①：圖片要不要走 Next 的「自動最佳化」

**白話**：`next/image` 有兩種用法。一種是「幫你把圖片轉小、轉 webp」（最佳化），另一種是「原圖直出，只是換個寫法」（`unoptimized`）。
問題是：**這個網站的正式環境（Docker 映像）現在根本跑不了最佳化**——一開最佳化，正式站上**每張圖都會變成破圖**（伺服器對圖片請求回 500）。
理由是 Next 對「standalone 打包 + 沒裝 `sharp`」這個組合硬性拒絕（背景 §B-4，原始碼已核）。而本機 `yarn dev` 看不出來（dev 模式會退回內建轉檔器），所以**這是一個 build 綠、dev 綠、上線才炸的陷阱**。
所以現在只有兩條路：要嘛全部原圖直出（跟現在一模一樣），要嘛先加 `sharp` 套件（裁決點 ②）。

| 選項 | 內容 | 評估 |
|---|---|---|
| **甲（每張 `unoptimized`）** | 10 處 `<Image>` 各自加 `unoptimized` prop；`next.config.js` ⛔ 不動 | 外觀零差異、不需 `sharp`、不需 `remotePatterns`（背景 §B-2：`unoptimized` 時 loader 完全不被呼叫，hostname 檢查不會跑）。但 10 處各寫一次；**日後任何人新增一張 `<Image>` 忘了寫 `unoptimized`，正式站那張圖就是 500**，且 dev/build 都不會警告 |
| **乙（走最佳化 + `remotePatterns` 白名單）** | `next.config.js` 加 `images.remotePatterns` 列 `www.paypalobjects.com`、`namelessrealms.com`、Discord CDN；10 處都不寫 `unoptimized` | 拿到 `next/image` 的真正價值（自動縮圖、webp、srcset）。**但必須先過裁決點 ② 加 `sharp`**，否則正式站全破圖；外觀**會**有可量化差異（`currentSrc` 變 `/_next/image?url=…`、多 `srcset`），⛔ 不符「最小改法」；Discord CDN 的真實 hostname ⛔ 未實查（只有架構師本人登得進） |
| **丙（全站 `images.unoptimized: true`）** | `next.config.js` 加一行 `images: { unoptimized: true }`；10 處 `<Image>` **都不寫** `unoptimized`（背景 §B-2：`config.unoptimized` 會強制每張都 unoptimized） | 外觀零差異、不需 `sharp`、不需 `remotePatterns`；**一行設定把「本 repo 現況跑不了最佳化」這件事變成機器強制**，日後新增圖片不會誤踩 500 陷阱；元件改動最小（只換標籤 + 加 `width`/`height`）。代價：日後要開最佳化時必須連 `sharp` 一起處理（但那本來就是必要條件）；`next.config.js` 多一行（`yarn build` 會驗它） |

**建議：丙。** 理由：架構師已裁「最小改法」，而丙是元件端改動最少的一條；更重要的是它把**正式環境的真實限制**（standalone 無 `sharp` ⇒ 最佳化端點必 500）寫成設定，讓它不再依賴每個人記得在每張圖上加 prop。
甲與丙的外觀結果**完全相同**（都是原 URL 直出），差別只在「靠人記」還是「靠設定」。乙是正確的長期方向，但它不是「最小改法」，且必須連同裁決點 ② 一起裁——建議留給日後另開一筆（可在 verification 建議）。
⚠️ 無論選哪個，「四頁 DOM 裡沒有任何 `<img>` 的 `currentSrc` 指向 `/_next/image`」都要在驗收 P5 用度量 JSON 證明（⛔ 不是 0 命中就算，見 P5 的配對正控）。

### 裁決點 ②：要不要新增 `sharp` 套件（技術棧層）

**白話**：`sharp` 是 Next 官方推薦的圖片轉檔套件。這個網站沒裝它。**只有在裁決點 ① 選了乙（走最佳化）時，才需要裝**；選甲或丙就完全不需要。
裝它是技術棧變更（`package.json` + `yarn.lock` + Docker 映像會變大、alpine 底下要驗預編譯二進位能不能用），依 `CLAUDE.md` 技術棧節，這要架構師點頭，規劃側與實作側都⛔ 不得自己加。

| 選項 | 內容 | 評估 |
|---|---|---|
| **甲（不加）** | 維持 `package.json` 現狀；⇒ 裁決點 ① **只能選甲或丙** | 零技術棧變更、`yarn.lock` 零變動；本包維持「最小改法」 |
| **乙（加 `sharp`）** | `yarn add sharp`；⇒ 裁決點 ① 可選乙 | 開放最佳化路線；但 `yarn.lock` 變、Docker image 變大、`node:20-alpine` 下的 `sharp` 二進位相容性⛔ 未實查（需真的 `docker build` 才驗得到，而本 repo 打 tag 就發版、沒有 build CI 可擋）；範圍從「換標籤」擴成「換技術棧」 |

**建議：甲（不加）。** 理由：與裁決點 ① 建議丙配套；本包的完成判準只要 lint 重新生效，⛔ 不需要為此換技術棧。若架構師想要最佳化價值，建議另開一筆（「加 `sharp` + `remotePatterns` + 拿掉 `images.unoptimized`」），那時再有外觀差異的驗收設計。

### 裁決點 ③：每張圖給 `width`/`height`，還是用 `fill`

**白話**：`next/image` 硬性規定每張圖要嘛給寬高數字，要嘛用 `fill`（自動撐滿父層）。不給會在 dev 模式直接炸頁（背景 §B-3）。
現在這 10 張圖**尺寸全部是用 Tailwind class 定的**（例如 `w-10 h-10`、`w-full h-full`），所以給的寬高數字**只當「長寬比提示」**，CSS class 仍然蓋過它 ⇒ 大多數位置給什麼數字都不會改版面；**只有兩處**例外（#2 PayPal 標誌只設寬、#3 團隊合照 `h-auto`）——那兩處的比例**必須給對**，否則圖片載入前的佔位高度會變。

| 選項 | 內容 | 評估 |
|---|---|---|
| **甲（全部 `width`/`height`）** | 10 處都給像素數字：固定 `src` 的用真實尺寸；由陣列／prop 驅動、來源尺寸不一的（#4、#5、#6、#10）用一組**名目值**（父層已用 CSS 固定尺寸 ⇒ 名目值不影響版面），建議表見「實作要點」 | 不注入任何 inline style（`fill` 會注入 `position:absolute; inset:0; width/height:100%`，背景 §B-5）⇒ DOM 差異最小；統一規則好審。⚠️ #2、#3 兩處尺寸必須實量（驗收 P0-C） |
| **乙（全部 `fill`）** | 10 處都用 `fill`，父層要 `position: relative` | #7 HomeHero 與 #8 Navbar 的 logo 尺寸寫在 `<img>` **自己**的 class（`w-32 h-32` / `w-10 h-10`），父層是 flex、⛔ 不是定尺寸的 relative 盒 ⇒ `fill` 會直接改版面；#1 的 `p-12` 在 `<img>` 自己身上，與 `fill` 的 inline `width:100%` 互動⛔ 未實查。⛔ 不符最小改法 |
| **丙（混用）** | 固定 `src` 用 `width`/`height`；陣列／prop 驅動的 #4、#5、#6、#10 用 `fill` | 避免「名目值」這個看起來彆扭的做法；但 #4 的 `w-32 h-32` 盒與 #5/#6 的 `aspect-square` 盒已經是 relative 定尺寸盒，`fill` 只是把既有 class 再用 inline style 寫一次；兩套規則要審兩次 |

**建議：甲。** 理由：10 處父層或自身都已由 CSS 定死尺寸（規劃側逐處 Read 核過，見背景 §A 表「尺寸由誰定」欄），`fill` 在這裡沒有任何額外價值、卻會注入 inline style 並在 #7/#8 改版面。
名目值的做法要在 plan 裡寫明理由（「父層 CSS 定尺寸，屬性只是比例提示」），且 #2、#3 必須用實量值。

### 裁決點 ④：`#9` Navbar 登入後的 Discord 頭像（`src` 可能是空字串）

**白話**：Navbar 右上角登入後會顯示 Discord 頭像，程式寫的是「有頭像網址就用、沒有就給空字串」。
規劃側核了 Next 原始碼：**空字串⛔ 不會炸頁**（背景檔原本推測會丟例外，這點檔案層核出來是錯的），但在 dev 模式會在瀏覽器 console 印一條紅字 `Image is missing required "src" property`（背景 §B-6）。
另外這張圖**只有架構師本人登入才看得到**，所以它的外觀證據要嘛由架構師親自登入拍，要嘛據實標「待人工」。

**(a) 怎麼改**

| 選項 | 內容 | 評估 |
|---|---|---|
| **甲（條件渲染）** | `session.user?.image` 有值才渲染 `<Image src={session.user.image} …>`，沒有就不渲染那個 `<img>`（外層的 `{session && (…)}` 與登出按鈕不動） | 拿掉空字串路徑 ⇒ dev console 不會有紅字；DOM 在「有頭像」時與現在**完全相同**；「沒頭像」時少一個 32×32 空圈——但 next-auth Discord provider 的 `profile()` 一律會給 `image`（有頭像用 CDN、沒頭像用 Discord 預設頭像），⛔ 未實查但可由 `node_modules/next-auth/providers/discord.js` 檔案層核（實作側必查）⇒ 「沒頭像」分支實務上到不了 |
| **乙（直接換、保留 `\|\| ""`）** | `<Image src={session.user?.image \|\| ""} width={32} height={32} …>` | 改動最少；但空字串時 dev 會印 `console.error`（違反驗收 P4「無執行期錯誤」的判準，除非明文豁免）；production 靜默渲染 `<img src="">`（與現況相同） |
| **丙（保留 `<img>` + `eslint-disable-next-line`）** | 這一處不換，用註解豁免規則 | 等於留一個洞：完成判準表面滿足（lint exit 0），但 10 處只修 9 處，`CLAUDE.md`「CI 現況」措辭要寫成「9 處已修、1 處豁免」 |

**建議：甲。** 理由：它讓「空 `src`」這條路徑從程式裡消失，而不是靠 Next 的容錯；且在唯一到得了的分支（有頭像）DOM 與現在一模一樣。⚠️ 實作側在 plan 裡先檔案層核 `next-auth` Discord provider 的 `profile()` 是否恆給 `image`，核到就引行號，核不到照樣選甲（甲不依賴這個事實，只是讓「少一個空圈」的顧慮消失）。

### 裁決點 ⑤：`#10` ServerSection 的伺服器卡片圖，外觀證據怎麼拿

**白話**：首頁的「伺服器卡片」那張圖，在**目前硬碟上的版本**根本不會顯示（卡片清單被清空了，那是長期沒 commit 的舊改動）；只有 **git 裡的版本**（HEAD）會顯示一張。
架構師已裁「commit 只收 img 那幾行」⇒ 進 commit 的是「HEAD 版 + 換 img」，但這個版本在硬碟上⛔ 不存在，要另外開一個乾淨目錄才跑得起來。
問題：這張圖的改前／改後截圖，要不要真的在那個乾淨目錄跑起來拍？

| 選項 | 內容 | 評估 |

### 裁決點 ⑥：截圖與度量 JSON 要不要進 git

**白話**：外觀證據有兩種檔：PNG 截圖（每張幾百 KB 到 1 MB，改前改後至少 8 張以上）與 JSON 度量（每檔幾 KB）。進 git 就永遠留在歷史裡、每次 clone 都要拉；不進 git 就只在這台電腦上。架構師人工看圖是在**這台電腦**看，跟進不進 git 無關。
