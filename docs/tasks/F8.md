## 目標
補回 ESLint 設定檔，使 `yarn lint`（= `next lint`）**真的 lint 到檔案、真的會在違規時以非 0 離開**；
並以**負向對照**（故意寫違規碼 → 證明會 fail → 移除）證明這道閘門存在。

`next lint` 無設定檔 exit 0（F8 本身）、`git check-ignore` 對已追蹤檔恆回不忽略（F4）、
`--debug` 輸出不走 stdout 導致 grep 0 命中差點寫成「沒警告」（2026-09-07）。

### 裁決點 ①：範圍——設定補上後，既有違規怎麼辦

白話：設定檔一補上，27 個從沒被 lint 過的檔案大概會噴一堆問題。這次要修到哪？

⚠️ **關鍵事實（檔案層已核，影響每個選項的風險）**：`next build` 本身也會跑 ESLint
（`node_modules/next/dist/build/type-check.js` 第 135 行呼叫 `verifyAndLint`；
`node_modules/next/dist/lib/verifyAndLint.js` 第 52–54 行對 **error 級**違規丟 `CompileError` ⇒ **build 失敗**；
warning 級⛔ 不會讓 build 失敗，因 build 期 `maxWarnings` 預設 `-1`）。
`next.config.js` 目前**沒有** `eslint.ignoreDuringBuilds`（Grep 無命中）。
⇒ **只要設定檔一進版控，若既有碼含 error 級違規，`yarn build` 與 Dockerfile 的 `npm run build`（發版路徑）會一起變紅。**
⚠️ 既有碼有幾條 error / 幾條 warning：**⛔ 未實查**——要跑了才知道（見下方「勘查」）。

| 選項 | 內容 | 風險 / 代價 |
|---|---|---|
| **甲** | 只補設定檔，跑一次把違規清單（檔名 / 規則 / 等級 / 條數）記進 verification，**一條都不修** | 若有 error 級違規 ⇒ `yarn build` 從此紅、**下一次打 tag 發版會失敗**。閘門存在但同時把發版擋死。 |
| **乙** | 補設定檔 + **修完全部**違規（error + warning），目標 `yarn lint --max-warnings 0` 綠 | 規模未知；改動可能散落 27 檔；且可能碰到工作樹三個**帶未 commit 舊改動**的檔（見裁決點 ④）。 |
| **丙** | 補設定檔，把噴出來的規則在設定檔裡**降級或關閉**讓 lint 立刻綠，另立任務逐步收緊 | `--max-warnings 0` 之下「降成 warn」等於沒降，只能「off」⇒ 對那些規則又變回**空測**，與 F8 存在理由相悖。 |
| **丁** | 補設定檔 + **只修 error 級**（守住 `yarn build` 與發版路徑不紅）；warning 記清單、另立 F{n} 修 | `yarn lint --max-warnings 0` 在 warning 修完前仍紅 ⇒ 驗收報告要據實寫「error 0 / warning N，嚴格指令尚紅」；需另開一筆 backlog。 |

**建議：丁**，附兩個前提：
1. **先勘查再定案**：實作側在 `F8-plan.md` 階段先做一次**勘查**（暫放設定檔 → 跑 `yarn lint` → 把 error / warning 各幾條、落在哪些檔貼進 plan → 把暫放的設定檔移除），
   讓 plan-review 時架構師看到**實數**再確認是丁、還是規模小到可直接升級為乙。
2. 若 error 級違規落在裁決點 ④ 的三個檔，先停下回報。

理由：F8 的核心是「閘門要存在且會擋」，⛔ 不是「把所有 warning 清零」；
丁在規模未知下把「不能弄壞發版路徑」放第一位，同時⛔ 不像丙那樣用「off」再造一個空測。
乙不是不行，但要等勘查數字出來才知道是否值得一次做完。

| 選項 | 內容 | 評估 |
|---|---|---|

### 裁決點 ③：lint 覆蓋範圍——要不要把 `data/` 與 `middleware.ts` 納進來

白話：`next lint` 預設只看五個目錄，本 repo 有 4 個檔在預設範圍外。要不要把它們也納入？

**檔案層已核的事實**：
- 預設目錄 = `app` / `pages` / `components` / `lib` / `src`（`node_modules/next/dist/lib/constants.js` 第 235–241 行）。
- 本 repo 待 lint 的 27 個 `.ts/.tsx`（Glob 實數）分佈：`app/` 12、`components/` 12、`data/` 3。
  ⇒ 預設只會 lint **24 個**；**`data/` 3 檔**與根目錄 **`middleware.ts`**（不在 27 之內）都在預設範圍外。
- 覆蓋方式：`next lint` 有 `--dir` 與 `--file` 旗標；沒給 `--dir` 時讀 `next.config.js` 的 `eslint.dirs`
  （`node_modules/next/dist/cli/next-lint.js` 第 73–74、121 行）。build 期也讀 `eslint.dirs`（`type-check.js` 第 135 行）。

| 選項 | 內容 | 評估 |
|---|---|---|
| **甲** | 維持預設五目錄，`data/` 與 `middleware.ts` 不 lint | 最小改動；但 `middleware.ts` 是鐵則 2 的一半、`data/` 是內容改動唯一落點，兩者恰好是最該守的。 |
| **乙** | `next.config.js` 加 `eslint: { dirs: ['app', 'components', 'data', 'lib', 'middleware.ts'] }` | lint 與 build 共用同一份範圍、script 不用改。⚠️ **`dirs` 裡放檔案路徑（`middleware.ts`）是否被接受：⛔ 未實查**（程式碼把它當「目錄」命名，但最後交給 ESLint `lintFiles`，ESLint 本身接受檔案）。 |
| **丙** | 改 `package.json` script：`"lint": "next lint --dir app --dir components --dir data --dir lib --file middleware.ts"` | 一定可行（旗標存在）；但 build 期不讀 script ⇒ build 與 lint 範圍不一致，`data/` 的 error 只在 `yarn lint` 擋、build 不擋。 |

**建議：乙**；若勘查時發現 `dirs` 不吃檔案路徑，退為「乙的目錄部分 + 丙的 `--file middleware.ts`」混合，並在 plan 寫明。
理由：閘門應該在 lint 與 build 兩處同一套；`middleware.ts` 不該是唯一不被 lint 的原始碼。
⚠️ 無論選哪個，驗收要**證明覆蓋數**（見驗收 P3），⛔ 不得以「設定寫了」當作已覆蓋。

### 裁決點 ④（條件觸發）：違規落在三個帶未 commit 舊改動的檔時怎麼辦

白話：工作樹有三個檔早就帶著跟 F8 無關的改動（`app/layout.tsx`、`app/staff/page.tsx`、`components/ServerSection.tsx`，
`CLAUDE.md` 地雷第 6 條）。如果 lint 要修的地方剛好在這三檔，修完之後**同一個檔裡會混著兩種改動**，逐檔 `git add` 也分不開。

| 選項 | 內容 |
|---|---|
| **甲** | 這三檔的違規**這次不修**，記進清單、留給處理舊改動的那筆任務 |
| **乙** | 用 `git add -p` 只挑 F8 的 hunk 進 commit（需人工逐 hunk 確認，並在 verification 貼 `git diff --cached --stat`） |
| **丙** | 先由架構師決定那三個舊改動的去留（另案），F8 等它收斂後再修這三檔 |

**建議：甲**（若那三檔沒有 error 級違規）；若有 error 級（會擋 build），停下回報架構師選乙或丙。
理由：F8 ⛔ 不該替別的任務決定那三個舊改動的命運。
⚠️ 勘查時**必須**把違規的檔案分佈貼出來，這點才裁得了。
